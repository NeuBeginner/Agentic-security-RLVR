## 1. Архитектура целостности групп GRPO (Group Relative Policy Optimization)

В алгоритме GRPO нормализованные преимущества ($A_i = \frac{r_i - \bar{r}}{\sigma_r + \epsilon}$) вычисляются **внутри** группы кандидатов, сгенерированных для одного и того же контекста.

### 1.1. Критерии сопоставимости внутри группы
В одну группу объединяются только completions, для которых строго совпадают:
- Исходный нормализованный промпт (проверка по криптографическому SHA-256 хешу `prompt_hash`).
- Исходный целевой смарт-контракт (`target_name`).
- Версия базовой модели и чекпоинта (`model_id`, `checkpoint_id`).
- Системный промпт (`system_prompt`).
- Условия генерации и спецификация вознаграждения.

### 1.2. Изоляция итераций (Refinement Isolation)
- Начальная генерация (`iteration=0`) и доработка по трейсу ошибки (`refinement_iteration >= 1`) используют **разные** шаблоны промптов (`build_analysis_prompt` vs `build_refinement_prompt`).
- Так как хеши промптов `prompt_hash` различаются, итерации уточнения формируют **отдельные группы**.
- Смешивание кандидатов первого прогона и доработанных кандидатов в одной группе GRPO строго запрещено.

### 1.3. Исключение ошибок инфраструктуры
- Любые кандидаты с категорией `INFRA_ERROR` (сбой компилятора, сетевой сбой Modal, нехватка памяти хоста) принудительно исключаются до формирования групп (`group_rollouts_by_prompt`).
- Сбои инфраструктуры не влияют на среднее вознаграждение $\bar{r}$, стандартное отклонение $\sigma_r$ и преимущества кандидатов.

## 2. Дизайн функции вознаграждения (Reward Shaping)

Вознаграждение опирается исключительно на результаты фактического исполнения и оракула состояния EVM:

| Категория (`ResultCategory`) | Вознаграждение | Обоснование и критерии |
|---|---|---|
| **`EXPLOIT_CONFIRMED`** | **`+1.00`** | Фактический пробой инварианта подтвержден Trusted State Oracle **И** независимо воспроизведен Replay Verifier со 100% детерминизмом. |
| **`INVARIANT_BREACH_UNREPLAYED`** | **`+0.50`** | Пробой зафиксирован в единичном прогоне, но независимый replay не подтвержден (промежуточный сигнал). |
| **`SAFE_RUN`** | **`-0.10`** | Эксплойт скомпилировался и выполнился успешно, но инварианты контракта устояли (нейтрально-отрицательный штраф). |
| **`RUNTIME_REVERT`** | **`-0.25`** | Эксплойт скомпилировался, но транзакция завершилась revert в EVM. |
| **`COMPILATION_ERROR`** | **`-0.50`** | Синтаксическая или семантическая ошибка компиляции `solc`/`forge`. |
| **`GENERATION_FORMAT_ERROR`** | **`-0.50`** | Модель нарушила спецификацию интерфейса `ExploitModule` (отсутствует `runExploit`, неверный конструктор). |
| **`CHEATCODE_DETECTED`** | **`-1.00`** | Попытка побега из песочницы или использование чит-кодов (`vm.*`, `forge-std/Test.sol`). |
| **`INFRA_ERROR`** | **`0.00`** | Нейтральный результат, исключается из оптимизации. |

> **Запрет манипуляций:** Невозможно получить положительное вознаграждение за текстовые сообщения в stdout/stderr. Выдача вознаграждения `+1.00` возможна только при подтверждении изменения состояния в EVM.

## 3. Происхождение данных (Dataset Provenance)

Каждая траектория сохраняет полный набор атрибутов происхождения:
- `trajectory_id`: Уникальный ID записи (`traj_{run_id}_{candidate_id}`).
- `candidate_id`: ID кандидата.
- `hypothesis_id`: ID проверенной гипотезы аудитора.
- `target_id` / `target_name`: Имя целевого контракта.
- `prompt_hash`: SHA-256 хеш нормализованного промпта.
- `model_id`: Модель, сгенерировавшая кандидат.
- `checkpoint_id`: Использованный чекпоинт весов/LoRA.
- `generation_iteration`: Номер раунда генерации/рефайнемента.
- `candidate_index`: Индекс кандидата в батче.
- `generated_token_ids`: Точный список ID сгенерированных токенов для исключения BPE-артефактов склейки.
- `token_provenance`: `model_generate`, `external_text_only`, `synthetic`.
- `dataset_partition`: `production`, `synthetic_control`, `test`.
- `dataset_split`: `train`, `val`, `holdout`, `test`.
- `is_synthetic`: Флаг синтетического контроля (всегда `False` для продакшн обучения).
- `trainable`: Допуск к обучению.
- `is_finalized`: Флаг завершения Replay (только `True` допускается в лоадер).

## 4. Защита от Data Leakage

В модуль `core/grpo_trainer.py` добавлен валидатор `validate_data_leakage_and_splits`:
1. **Протокольное разделение (Target Disjointness):** Смарт-контракты, входящие в `test` и `holdout`, **никогда** не пересекаются со сплитом `train`. 
2. **Изоляция хешей эксплойтов:** Эксплойты тестового набора не должны присутствовать в обучающей выборке.
3. **Изоляция синтетического контроля:** Записи с `is_synthetic=True` или `dataset_partition="synthetic_control"` блокируются от попадания в обучающий сплит.
4. **Проверка заземленности (Grounding Check):** Категория `EXPLOIT_CONFIRMED` требует строго `is_verified=True`, `reproduced=True`, `replay_status='CONFIRMED'`.

## 5. Fail-Closed Training Gate

**Статус:** `TRAINING_STATUS = BLOCKED`.

В коде реализованы жесткие защитные ворота:
- Любой прямой вызов `train_grpo_epochs()` или функции Modal `train_grpo_remote()` немедленно выбрасывает исключение `RuntimeError("FAIL-CLOSED SECURITY GATE: TRAINING_STATUS = BLOCKED")`.
- Оптимизационный шаг `optimizer.step()`, обновление весов и перезапись чекпоинтов заблокированы до выполнения всех критериев валидации.
